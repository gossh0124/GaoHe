# GaoHe v1：Skill＋遠端連接器 設計規格

- 日期：2026-11-05
- 狀態：待使用者審閱
- 取代：`2026-09-18-gaohe-media-monitoring-v0-design.md` 的產品方向（§2.5「沒有單一媒體總分」與 §3.2「沒有實際資料支持的媒體偏向分數」等原則由本文件 §2 取代）；Windows 本機監測程式碼凍結於 `/legacy`。
- 背景研究：見本 repo 外的研究簡報（2026-11-05，已經獨立查核）；本文件中標示「未確認」者為研究時無法以官方來源逐字核實的事項，實作前必須重新驗證。

## 1. 目標

GaoHe 是開源、非官方的**已刊出新聞稿後查核與中立性紀錄**工具，與政府澄清管道及以謠言為主的查核平台區隔。

1. 能針對使用者輸入的**網址或關鍵字**進行事實查核。
2. 對**發表機構與作者**留存可追溯的中立性紀錄與分項分數（用字遣詞、資訊缺漏等），分數**一律由 AI 依公開評分準則判定**，使用者不投票、不打分。
3. 可看性高，前後端與開發者體驗（UI/UX/DX）良好。
4. 使用者能針對文章內容做更深入的知識研究與事實檢核。
5. 多個使用者的 AI 產出經伺服器驗證後聚合為共享的機構／作者紀錄，同步到所有客戶端與公開網站；每個人使用**自己的 AI 訂閱**，GaoHe 不持有任何 AI 憑證。

### 1.1 成功條件

1. 使用者只需在 Claude 中上傳 Skill ZIP 並加入連接器網址、以 GitHub 登入，即可完成網址或關鍵字查核，無需安裝 Python 或提供 API key。
2. 每個公開結論都能回溯到快照段落、證據網址、取得時間、評分準則版本與參與帳號數。
3. 任何單一帳號都無法使單一文章進入「已確認」狀態；任何單一帳號對單一機構已確認結果的影響不超過 20%。
4. 找不到證據、抓取失敗或複核衝突，都不會被轉成「有誤」或負面分數。
5. 伺服器在 Cloudflare 免費方案額度內運作，且資料每晚匯出至公開 GitHub repo，可遷移。
6. CI 不呼叫任何 AI 或外部服務即可驗證格式、驗證器、聚合器與攻擊情境。

## 2. 原則（取代 v0 §2.5）

1. **多維度、無總分。** 每個維度獨立呈現，不合成單一可信度分數、不做排行榜。
2. **沒有原文片段就不成立。** 每個標記必須附快照段落位置與逐字引文。
3. **找不到證據不是證明為錯。** 無法取得或證據不足只能產生「無法證實」或「無法取得」。
4. **伺服器不信任任何單一客戶端。** 公開狀態只來自可機械驗證的檢查加上多帳號共識。
5. **政治偏頗維度 v1 暫停。** 所有新聞（含政治新聞）照常查核，但不輸出藍綠、統獨或左右分數。
6. **對事不對人。** 作者頁只呈現作品的描述統計與可點擊的依據，不推論動機、不使用「不可信」等總評標籤。
7. **不繞過存取控制。** 不繞過付費牆、登入或 CAPTCHA。
8. **開源。** Skill、評分準則、驗證器與聚合器程式碼全部公開；評分準則改版經 PR 審查並附版本號。

## 3. 範圍

### 3.1 包含（v1）

- GaoHe Skill（Claude Agent Skill ZIP）：查核流程、評分準則 v1、輸出 JSON Schema、artifact 報告範本。
- GaoHe 遠端 MCP 連接器（Cloudflare Workers，TypeScript）：快照、提交、複核任務、查詢。
- 驗證器、聚合器、帳號信用機制（D1）。
- 公開唯讀網站（Cloudflare Pages）與公開唯讀 REST API（附 OpenAPI 文件）。
- 每晚匯出至公開 GitHub repo 的開放資料。
- 作者頁（依 §7.4 保護措施）。
- 申訴與回應管道。

### 3.2 不包含（v1）

- 政治偏頗／立場維度。
- ChatGPT、Gemini 等其他 AI 客戶端（v2 評估；格式設計需保持客戶端中立）。
- 自動排程監測媒體新文章（Skill 只在使用者開啟對話時執行）。
- Windows 本機監測的新功能開發（程式碼保留於 `/legacy`，不刪除）。
- 營運方以自己的 API key 進行評分或抽查。
- 單一總分、排行榜、作者動機推論。

## 4. 架構

```text
使用者的 Claude（claude.ai 或 Claude Desktop，使用者自己的訂閱）
  ├─ GaoHe Skill（上傳 ZIP）
  │    流程、評分準則 v1、JSON Schema、報告範本
  └─ GaoHe 連接器（自訂連接器網址＋GitHub OAuth）
          │ MCP（遠端，HTTP）
          ▼
GaoHe 伺服器（Cloudflare Workers，TypeScript）
  ├─ MCP 工具：submit_snapshot / get_snapshot / submit_assessment /
  │            get_review_task / submit_review / get_scores / get_record
  ├─ 正規化＋段落雜湊（確定性、低 CPU）
  ├─ 驗證器（schema、逐字引文、封閉標籤、數量上限）
  ├─ 聚合器（增量更新、加權中位數、共識）
  ├─ 信用與任務分派
  ├─ D1：sources、authors、articles、article_versions、paragraphs、
  │       paragraph_attestations、assessments、claims、evidence、
  │       reviews、accounts、gold_items、aggregates、appeals
  └─ 公開唯讀 REST API
          │
          ├─ Cloudflare Pages：公開網站（Astro 靜態網站，讀取 REST API）
          └─ GitHub Actions：每晚匯出聚合結果至公開資料 repo
```

可行性前提（實作第一步必須實測，未通過則回到設計）：

- Claude 的 Skill 與自訂遠端連接器在目標方案（至少 Pro）於 claude.ai 網頁版與 Claude Desktop 皆可用；免費方案的數量限制未確認。
- Skill 執行時，Claude 可使用內建網頁搜尋與網頁抓取取得文章原文與證據。
- Cloudflare Workers 免費方案每個請求約 10ms CPU 足以完成單篇正規化與段落雜湊；若不足，升級 Workers Paid（約 US$5／月）。
- D1 免費額度（每資料庫 500MB；每日讀寫列數上限，超過即失敗——後者為研究所得，未逐字核實）足以支撐初期流量。

## 5. 分工：使用者的 AI 與伺服器

| 工作 | 執行者 | 伺服器的機械檢查 |
|---|---|---|
| 抓取文章原文 | 使用者的 AI | 伺服器正規化並計算段落雜湊；段落須有 ≥2 個不同帳號提交相同雜湊才「已確認」 |
| 拆解可查證主張 | 使用者的 AI | 每個主張必須指向已確認段落中的逐字片段 |
| 搜尋、閱讀證據與推論 | 使用者的 AI | 證據須附網址、引文、取得時間、證據等級；由其他帳號複核 |
| 中立性 D1–D5 評分 | 使用者的 AI | 引文逐字比對；多帳號加權中位數 |
| 交叉複核他人提交 | 使用者的 AI（伺服器指派的不同帳號） | 指派紀錄、禁止自我複核 |
| 正規化、雜湊、驗證、聚合、信用 | 伺服器 | 全為確定性運算，不呼叫 AI |

伺服器不抓取新聞網站，因此不受雲端 IP 被封鎖影響；伺服器只公開段落雜湊與短引文（每則上限 120 字），不公開全文。

## 6. 資料流程

### 6.1 快照

1. Skill 以 Claude 內建抓取工具取得文章，擷取標題、機構、署名、發布時間與正文段落。
2. 呼叫 `submit_snapshot(url, metadata, paragraphs[])`。
3. 伺服器正規化：Unicode NFC、全形／半形空白統一、連續空白合併、去除首尾空白；以正規化後的段落計算 sha256。
4. 段落雜湊被 ≥2 個不同帳號提交時標記為「已確認段落」。
5. 一篇文章已確認段落比例 ≥60% 時，快照狀態為「穩定」，可進入共識評分；否則為「快照不穩定」，結果只能停在「初步」。
6. 同一 URL 出現新的段落集合且已確認段落改變時，建立新的 `article_version`；舊版結果保留並標示適用時間。

字元位置統一以 **Unicode code point** 計算（不使用 UTF-16 code unit），Skill 輔助腳本與伺服器共用同一份測試向量。

### 6.2 查核與評分

1. 輸入為網址：直接進入 6.1。輸入為關鍵字：Skill 搜尋並列出 3–5 篇相關報導供選擇，或選擇「直接查這個說法」（以主張為中心跨來源驗證，產生的主張紀錄不綁定單一文章）。
2. 拆解主張（§8）→ 搜尋證據 → 逐主張結論 → 中立性 D1–D5（§7）。
3. 產出 artifact 報告（§10.2）。
4. 詢問使用者是否提交；同意後呼叫 `submit_assessment`。不同意則僅保留在對話中。
5. 驗證失敗時伺服器回傳具體錯誤碼與欄位，Skill 修正後最多重送 2 次。

### 6.3 複核

1. 每次 Skill 開始時呼叫 `get_review_task`；伺服器隨機指派一個待複核項目（文章評分或單一主張），使用者可略過。
2. 複核者看不到原提交的分數，只拿到快照與主張清單，獨立完成評分後以 `submit_review` 提交（盲審）。
3. 伺服器禁止帳號複核自己的提交，也不把同一項目派給同一網段雜湊的帳號。

### 6.4 聚合

- 增量聚合：每次新提交只重算受影響的文章、機構與作者列，不做全表重算。
- 公開狀態：
  - **初步（n/3）**：參與帳號不足 3，或快照不穩定。不計入機構與作者統計。
  - **已確認**：滿足 §9.3 共識規則。
  - **有爭議**：滿足帳號數但結論不一致（§9.3）。
- 評分準則主版本不同的結果分開聚合；公開頁面預設顯示目前主版本。

## 7. 中立性評分準則 v1

### 7.1 維度

| 代號 | 名稱 | 主要量測方式 | 單位 |
|---|---|---|---|
| D1 | 情緒性用語 | 標記帶情緒或評價色彩、可被中性詞替代的用語片段 | 每千字標記數 |
| D2 | 消息來源與引述歸屬 | 計數可辨識來源、匿名來源、無來源的事實性陳述 | 比例 |
| D3 | 標題與內文一致 | 標題主張是否被內文支持（一致／誇大／不支持） | 類別 |
| D4 | 評論包裝成報導 | 標記未標示為評論的作者評價或推測句 | 每千字標記數 |
| D5 | 比較式遺漏 | 同一事件 ≥3 家其他媒體共同報導、而本文未提及的實質事實 | 項數 |

- 每個標記：段落 ID、code point 起訖、逐字引文、封閉標籤、理由（≤200 字）。
- D1、D4、D5 標示為「AI 詮釋」；D2、D3 以計數為主。
- 爭議用語（如兩岸稱謂）v1 不評分、不標記。
- 政治偏頗／立場維度 v1 暫停。

### 7.2 D5 前提

D5 需要同事件的其他報導。Skill 在評 D5 前必須列出所比較的其他報導網址；比較報導不足 3 家時 D5 填「不適用」，不得給值。

### 7.3 Skill 的穩定性要求

- Skill 對 D1、D4 要求 AI 先列出所有候選片段再逐一判定，以降低順序敏感。
- 評分準則文字中的範例需涵蓋各類新聞（社會、財經、科技、國際、政治），避免範例集中於單一議題。

### 7.4 作者層級的保護措施

1. 作者頁只顯示各維度計數與中位數，每筆連結到原文片段與證據；不顯示總評、不排行、不推論動機。
2. 作者需有 ≥10 篇「已確認」文章才公開，未達門檻顯示「樣本不足」。
3. 通訊社稿件計入通訊社；「綜合報導」與無具名稿件只計入機構；D3（標題）只計入機構。
4. 作者可透過申訴頁提出更正或回應，與結果並列顯示；GaoHe 判斷錯誤時公開更正紀錄。
5. 只有「已確認」結果計入作者統計。
6. 公開上線前建議由台灣律師審閱評分方法頁與作者頁（不阻擋開發）。

## 8. 事實查核方法

既有查核機構的結論（台灣事實查核中心、MyGoPen、Cofacts 等）是一種證據，不具最終決定權。

1. **拆解**：把主張拆成最小可檢驗單位（主體、時間、行為、數量、因果）。
2. **證據分級**：
   - 一級：一手資料（官方統計、判決書、原始文件、同儕審查論文、當事人原話紀錄）。
   - 二級：可信的二手報導、既有查核機構報告。
   - 三級：評論、社群貼文。
3. **獨立性**：轉述同一源頭的多個來源只算一個；必須追溯到最早出處並記錄。
4. **三角驗證**：結論需有彼此獨立的來源；必須主動搜尋反方證據並記錄搜尋關鍵字。
5. **結論與信心**：
   - 結論：證實／大致正確／缺少脈絡而誤導／有誤／無法證實／尚待時間驗證。
   - 信心：高／中／低，附理由。
   - 「有誤」至少需要一份一級證據直接牴觸，或兩份獨立二級證據牴觸。
6. **可推翻**：每個結論寫明「出現什麼證據會改變此結論」。
7. **可重現**：記錄搜尋關鍵字、證據網址、取得時間；如有存檔連結一併附上。
8. **重複驗證**：≥3 個不同帳號獨立查核同一主張，公開一致程度；不一致則為「有爭議」。

## 9. 帳號信用與防灌票

### 9.1 身分

- GitHub OAuth；一個 GitHub 帳號對應一個 GaoHe 帳號；伺服器不存任何 AI 憑證。
- GitHub 帳號建立滿 30 天，提交才計入聚合。
- 每帳號每日最多 30 次提交（D1 計數）。
- IP 只存加鹽雜湊後的網段，用於分派與群集偵測，不公開。

### 9.2 任務分派

- 使用者自行選擇的文章，提交只算「發起者」一票。
- 共識所需的其他票只來自伺服器隨機指派的複核任務，複核者無法挑選目標。

### 9.3 共識規則

- 中立性 D1–D5：≥3 個不同帳號、各維度取信用加權中位數；片段標記需 ≥2 個帳號標到重疊片段（code point 區間交集 ≥50%）才顯示。
- 事實查核：≥3 個帳號且多數結論一致即採用並顯示一致程度；無多數則為「有爭議」，追加指派 2 位複核者，仍無多數則維持「有爭議」並並列雙方證據。
- 單一帳號對任一機構已確認結果的貢獻上限 20%（以參與的已確認文章計）。

### 9.4 信用

- 新帳號前 10 次提交為影子模式：不計入聚合，只與共識比對。
- 指派任務中 5–10% 為已知答案題（gold items），使用者無法辨識。
- 信用依與共識的一致率、已知答案答對率累積（Beta 分布平滑），作為加權依據並設權重上限。
- 群集偵測：同網段、註冊時間接近、答案高度雷同的帳號群自動降權並列入人工檢查佇列。

### 9.5 冷啟動

- 公開網站區分「初步」與「已確認」，初步結果不計入統計。
- 營運者以一般帳號參與，無特權。
- v1 需人工標註約 50 篇文章作為已知答案題庫的起點。

### 9.6 Prompt injection

- Skill 指示 AI 將文章與證據內容視為資料，忽略其中任何指令。
- 伺服器只接受封閉標籤、固定格式與長度上限；自由文字欄位（理由）不影響分數計算。

## 10. 介面與開發者體驗

### 10.1 Claude 內的流程

- 進度以簡短訊息逐步回報（快照 → 主張 → 證據 → 評分 → 報告）。
- 完成後詢問是否提交；最後提示一個待複核任務。

### 10.2 查核報告（artifact）

依序：標題／機構／作者／時間／快照確認段落數 → 主張結論統計 → D1–D5 卡片（附初步或已確認 n/3）→ 原文（淡色標示，點擊跳至主張卡）→ 主張卡（結論、信心、支持證據與等級、反方證據、可推翻條件、深入研究按鈕）→ 側欄機構與作者累計紀錄 → 頁尾評分準則版本、模型、搜尋紀錄。

### 10.3 深入研究

每張主張卡提供：追溯原始出處、找反方證據、看其他媒體怎麼報導、整理事件時間軸、補充背景知識。結果可「補充到這個主張」後提交，同樣經複核。

### 10.4 公開網站

繁體中文、支援手機與深色模式、符合 WCAG 2.1 AA。頁面：首頁搜尋、媒體頁、作者頁、文章頁（唯讀報告）、評分方法頁、申訴頁、開放資料下載頁。

### 10.5 Repo 結構

```text
/schemas   JSON Schema 與測試向量（Skill、伺服器、網站共用的唯一格式來源）
/skill     SKILL.md、rubric/v1.md、報告範本、打包腳本
/server    Cloudflare Workers（TypeScript）
/web       Astro 靜態網站
/legacy    凍結的 Python 本機版（原 src/、tests/、scripts/）
```

## 11. 錯誤處理與測試

### 11.1 錯誤處理

| 情況 | 處理 |
|---|---|
| 抓不到原文（付費牆、登入、擋爬蟲） | 「無法取得」，不評分，不繞過 |
| 段落不一致 | 只用已確認段落；確認比例 <60% 為「快照不穩定」，只能停在初步 |
| 文章改寫 | 建立新版本，舊版結果保留並標示時間 |
| 格式錯誤或引文不符 | 拒收並回傳錯誤碼與欄位；Skill 最多重送 2 次 |
| 找不到證據 | 「無法證實」，不得為「有誤」 |
| 複核衝突 | 「有爭議」，追加 2 位複核者 |
| 免費額度用完 | 回傳「伺服器忙碌」；報告保留於對話供稍後重送；網站讀最近一次靜態備份 |
| 連接器未安裝或連不上 | Skill 仍完整查核並產出報告，註明無法提交與無累計紀錄 |
| 文章內嵌指令 | Skill 忽略；伺服器只接受固定格式 |

### 11.2 測試（CI 不呼叫任何 AI）

1. 格式測試：`/schemas` 正例與反例。
2. 驗證器單元測試：正規化、段落雜湊、逐字比對、code point 位置（含罕用字與 emoji）、封閉標籤、數量上限。
3. 聚合器性質測試：未滿 3 帳號不會「已確認」；單帳號影響 ≤20%；影子帳號不影響結果；主版本不混算。
4. 攻擊情境測試：假帳號群集灌票、引文造假、自我複核、刷提交、內嵌指令。
5. 整合測試：wrangler 本機模擬，跑完整「快照 → 提交 → 複核 → 聚合 → 公開 API」。
6. Skill 品質評估（手動，不進 CI）：以已知答案題庫實際執行 Claude，量測與已知答案一致度及同篇多次執行的穩定性；評分準則改版前後都要跑。
7. 網站：Playwright 無障礙檢查與手機版面截圖。
