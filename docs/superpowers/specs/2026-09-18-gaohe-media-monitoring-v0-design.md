# GaoHe 媒體監測與證據對照 v0 設計規格

- 日期：2026-09-18
- 狀態：待使用者審閱
- 範圍：固定媒體監測、文章版本、證據查證、同題對照、Windows 使用者流程
- 依賴：既有 Windows 原生基線與 GitHub CI；CD 仍暫緩

## 1. 問題本質

GaoHe 的核心工作不是替整篇新聞判定真假，也不是替媒體產生總體可信度分數，而是讓使用者能長期監測指定媒體，對每一篇新文章保留可回溯的主張、證據與同題差異。

核心鏈條：

```text
指定媒體
→ 新文章或文章版本
→ 可驗證主張
→ 外部證據
→ 同題媒體對照
→ 具實質性的發現
→ 原文局部標註與證據說明
```

成功條件：

1. 沒有 Python、RSS 或 Windows 工作排程背景的 Windows 使用者，可以透過 Release ZIP 完成設定、啟用、暫停與卸載。
2. 使用者可以監測固定媒體，不需要依賴關鍵詞硬篩選才不漏文。
3. 沒有新文章或文章內容沒有變更時，不重複呼叫 AI 或外部抓取服務。
4. 只有事實矛盾、實質跨媒體差異、推論超出證據三類問題可以形成 v0 的可見標註。
5. 每個可見標註都能回到原文、來源網址、證據片段、provider、抓取時間與人工確認狀態。
6. 來源失敗、搜尋摘要或證據不足不會被誤轉成錯誤判定。
7. API key 與分析資料保留在本機；卸載預設不刪除使用者資料。
8. CI 可以用 deterministic fixture 驗證主要流程，不呼叫真實 AI、搜尋或 Firecrawl API。

## 2. 第一原理與不可違反的事實

### 2.1 監測不是即時推送

一般新聞網站不會主動通知 GaoHe 頁面已更新。除非來源提供 webhook 或 WebSub，否則「網站更新才執行」在 v0 的實際形式是低成本輪詢：定期檢查 RSS、新聞列表或 sitemap，只有發現變更才進入深度分析。

### 2.2 主張不是問題

文章中的可驗證主張可以先進入背景紀錄，但不代表應該在原文上色。普通事件敘述、沒有重大差異的約略數字與尚未找到官方來源的主張，預設不形成可見問題。

### 2.3 搜尋線索不是證據

搜尋結果摘要可以幫助發現來源，但不能單獨形成事實矛盾或錯誤標註。可見標註需要可回溯的來源頁、正文或可引用片段。

### 2.4 找不到證據不是證明為錯

來源打不開、需要登入、被反爬、搜尋不到或 Firecrawl 額度不足，都只能產生「無法完成查證」、「搜尋範圍不足」或「待補查」狀態。

### 2.5 沒有單一媒體總分

事實準確性、報導框架與跨媒體差異是不同維度。v0 不建立媒體可信度總分、排名或排行榜。

## 3. 範圍

### 3.1 包含

- 固定媒體清單。
- RSS、新聞列表或 sitemap 的來源探索。
- 全量收集來源出現的新文章 metadata，不使用關鍵詞作硬排除門檻。
- 已知文章網址的本機直接抓取。
- 文章內容雜湊與版本紀錄。
- 主要 AI provider 的 provider-neutral 設定。
- AI 初步分析與候選問題提案。
- 只對候選問題進行外部證據查找。
- Firecrawl 作為選填的搜尋／抓取 fallback。
- 同題媒體分組與差異比較。
- 新文章收件匣、發現事項、同題對照、來源狀態。
- Windows 使用者層級工作排程。
- GitHub Release ZIP、`setup.cmd`、`uninstall.cmd` 的使用者流程設計。
- 本機 SQLite 監測資料。

### 3.2 不包含

- 整個網站的持續爬取。
- 以關鍵詞命中與否直接刪除文章。
- Windows Service 或常駐背景 daemon。
- 沒有實際資料支持的媒體偏向分數。
- 自動判定重要遺漏為問題。
- 單一「整篇文章真假」結論。
- 電子郵件、Discord 或其他外部通知。
- 單一 EXE 安裝器。
- CD、自動部署或遠端資料庫。
- 將文章快照或報告提交到公開 GitHub repo。

## 4. 使用者流程

### 4.1 一般使用者首次設定

一般使用者下載 GitHub Release ZIP，不需要 clone repo。`setup.cmd` 啟動本機設定流程：

1. 檢查 Python、資料目錄、網路與 Windows 工作排程能力。
2. 選擇主要 AI provider 並輸入自己的 API key。
3. 以最小請求測試 provider；錯誤訊息不得顯示 key。
4. 加入至少一家媒體與 RSS／新聞列表網址。
5. 測試來源，顯示最近文章與來源健康狀態。
6. 建立使用者層級工作排程。
7. 顯示監測摘要：媒體數、上次檢查、下次檢查、來源錯誤與新增文章。

Firecrawl API key 是選填；沒有 Firecrawl 不應阻止 GaoHe 使用本機直接抓取與主要 provider 可提供的能力。

### 4.2 日常使用

預設入口是新文章收件匣。使用者可以看到：

- 媒體、標題、發布時間與分析狀態。
- 是否屬於同題群組。
- 是否有待處理發現。
- 來源最近一次檢查結果。

一般文章不需要上色。只有已形成可見發現的文字才在原文上顯示低飽和度標註。

### 4.3 暫停與卸載

使用者可以在本機介面中暫停監測、立即檢查或移除自動監測。`uninstall.cmd` 預設移除工作排程與程式環境，但保留 `.env`、SQLite 資料庫、文章版本與報告；完整清除資料必須是明確的額外動作。

## 5. 監測與資料流

```text
Windows 工作排程
→ gaohe watch --once
→ 讀取 RSS／新聞列表／sitemap
→ 記錄所有新文章 metadata
→ URL 與內容雜湊去重
→ 新文章或新版本才抓取與初步分析
→ 候選問題才查找外部證據
→ 建立主張、證據、同題與發現紀錄
→ 更新本機 UI 與來源狀態
```

### 5.1 來源探索

每家媒體設定至少包含：

- 顯示名稱。
- RSS、新聞列表或 sitemap URL。
- 啟用狀態。
- 可選的監測描述。
- 可選的提示關鍵詞與排除提示。

提示關鍵詞只用於排序或提供模型參考，不得作為文章是否收錄的硬門檻。初始實作以所有新文章 metadata 先入庫，再做相關性分流。

### 5.2 變更偵測

- 同一 URL 且內容雜湊相同：跳過深度分析。
- 同一 URL 但內容雜湊不同：建立新文章版本並重新分析。
- 新 URL：建立新文章並分析。
- 來源 HTTP／RSS 失敗：記錄來源失敗，不產生「沒有新文章」結論。

### 5.3 排程

v0 使用 Windows 使用者層級工作排程，不建立 Windows Service。排程執行一次短命的 `watch --once`，沒有新內容時正常結束。工作排程設定應允許電腦錯過排程後在下次可執行時補做一次檢查。

初始預設以每小時檢查一次作為低成本變更偵測；使用者不必在首次設定時處理複雜排程參數。

## 6. Provider 與查證管線

### 6.1 能力分工

```text
來源探索：RSS／新聞列表／AI web search／Firecrawl Search
網頁抓取：本機直接 HTTP／Firecrawl Scrape
證據評估：使用者選擇的主要 AI provider
```

### 6.2 預設順序

1. 監測來源發現新文章。
2. 以 Python 標準 HTTP 抓取已知網址。
3. 主要 AI provider 提出候選問題。
4. 需要外部來源時使用 provider 原生 web search；沒有此能力時使用選配搜尋 provider 或 Firecrawl Search。
5. 已知證據網址直接抓取失敗時，才使用 Firecrawl Scrape fallback。

Provider 設定不得與 Gemini 專屬名稱綁定。每個 provider 的名稱、模型、能力與錯誤都要被記錄。

### 6.3 證據最低要求

證據紀錄至少保存：

- source URL。
- page title。
- 發布或更新時間（若來源提供）。
- 正文或短引文。
- provider。
- 抓取時間。
- HTTP／抓取狀態。
- 內容雜湊（可取得時）。

只有搜尋摘要時，狀態為「僅找到搜尋線索，尚未取得原始頁面」，不可形成事實矛盾標註。

### 6.4 查證狀態

v0 使用文字狀態，不使用顏色表示支持程度：

- 未查證。
- 已查證，來源一致。
- 已查證，來源有差異。
- 找到反向證據。
- 搜尋範圍不足。
- 待人工判讀。

## 7. 主張、發現與可見標註

### 7.1 三層模型

```text
主張抽取：所有可驗證主張，可存在於背景紀錄
證據評估：判斷來源支持、差異或反向證據
可見發現：只有具實質問題的內容才進入原文標註
```

### 7.2 可見發現門檻

概念規則：

```text
可見發現
= 與監測範圍相關
  且可由外部資料查核
  且存在事實矛盾、實質跨媒體差異或推論超出證據
```

普通事件敘述、沒有重大差異的約略數字、只有找不到官方來源、只有模型覺得語氣可疑，都不產生可見標註。

### 7.3 v0 可見標註類型

1. **事實矛盾**：可靠來源與文章主張直接衝突；使用淡紅色。
2. **實質跨媒體差異**：同一重要主張的來源描述不同，且會影響理解；使用淡藍色。
3. **推論超出證據**：文章把推測、因果或政治意義寫成已證實事實；使用淡紫色。

「重要遺漏」暫不自動形成 v0 可見標註，僅保留人工備註能力。

### 7.4 數字主張

「近 500 位」不使用固定百分比自動判錯。先判斷原文是否為約略表述，再比較來源是否有實質差異；450、500、520 若語意與事件規模一致，保留為背景主張，不產生問題標註。

### 7.5 視覺語意

```text
螢光顏色 = 問題類型
右側文字狀態 = 證據狀態
```

原文使用低飽和度背景與底線，避免遮住字詞。未標註不代表已證實，只代表目前沒有形成可見發現；這類說明放在說明頁或展開區，不在每篇文章重複佔用主要閱讀空間。

## 8. 同題分組與對照

同題分組使用事件時間、人物／機構、地點、核心事件、標題與摘要語意等訊號。標題相似不是充分條件。

- 只有一篇文章：可做證據查核，不產生跨媒體差異。
- 至少兩篇可能同題文章：顯示共同事實與候選差異。
- 模型無法確定：標記「可能同題」並等待人工確認。

同題對照只比較重要主張，不把每個用詞差異都當成問題。

## 9. 本機資料與隱私

### 9.1 儲存位置

```text
.env
→ API key 與本機設定

gaohe.db
→ sources、source_checks、articles、article_revisions、topics、claims、findings、evidence、runs

reports/
→ 使用者明確匯出的報告
```

`.env` 不進 SQLite，也不進 Git。文章內容、快照與報告不進公開 repo。

### 9.2 外部傳送告知

設定頁與 README 必須說明：

- 文章內容可能送到使用者選擇的 AI provider。
- 啟用 Firecrawl 時，網址或頁面內容可能送到 Firecrawl。
- Firecrawl 是外部服務，可能有 credits、速率限制、403、登入牆、付費牆、JavaScript 頁面與抓取不完整等限制。
- GaoHe 不繞過登入、付費牆、CAPTCHA 或網站安全控制。

## 10. 失敗處理與成本控制

- API key 錯誤：停止該次分析，保留文章與來源資料。
- HTTP／RSS 失敗：標記來源失敗，不宣稱沒有新文章。
- Firecrawl 或 web search 額度不足：標記候選問題待補查，不進入無限重試。
- provider 逾時或 429：採有限次重試，記錄失敗原因。
- 每日或每月預算達上限：停止新的外部查證，保留待處理項目。
- 沒有新文章：AI 呼叫次數為零。
- 文章未變更：深度分析次數為零。

## 11. 使用者介面

主要入口包含四個區塊：

1. **新文章收件匣**：全部新文章與分析狀態。
2. **發現事項**：三類可見問題與證據鏈。
3. **同題對照**：至少兩篇同題文章的共同事實與差異。
4. **來源狀態**：每家媒體的最近檢查、來源健康與錯誤。

不提供 v0 媒體總分、排行榜或自動外部通知。

## 12. 驗收與測試

### 12.1 Deterministic CI

CI 不呼叫真實 provider。使用 fixture 與 fake provider 驗證：

- RSS 無變化不產生 AI 呼叫。
- 新 URL 只建立一篇新文章。
- 相同內容不重複分析。
- 相同 URL 的新雜湊建立新版本。
- 來源失敗不轉成「沒有新文章」。
- 沒有證據時不建立可見標註。
- 只有搜尋摘要時不建立事實矛盾。
- 只有一篇文章時不建立跨媒體差異。
- 工作排程安裝／移除的資料處理符合預期。

### 12.2 本機人工驗證

使用固定新聞案例驗證：

- 普通事件敘述不被過度標註。
- 事實矛盾、跨媒體重大差異、推論超出證據能被分開。
- 450、500、520 的約略數字不被自動判錯。
- 原文與右側證據可以互相定位。
- provider 與抓取時間可追溯。

### 12.3 使用者驗證

由沒有 Python、RSS 或工作排程器背景的 Windows 使用者完成：

```text
Release ZIP
→ setup
→ API key
→ 一個媒體來源
→ 啟用監測
→ 看懂狀態
→ 暫停
→ 卸載並保留資料
```

### 12.4 小規模實際監測

在正式擴大前，監測少量媒體一段時間，記錄每日文章量、分析篇數、token、web search 次數、Firecrawl credits、來源失敗與人工修正次數。這些數據用來決定是否需要關鍵詞分流、單一 EXE 或更複雜排程。

## 13. 刻意延後與回加條件

依刪除優先原則，以下項目刻意不加入 v0：

- **整站爬取**：只有 RSS／列表長期無法覆蓋監測範圍時才考慮。
- **關鍵詞硬過濾**：只有文章量已證明造成成本或處理壓力時才考慮；即使回加也只能作排序提示，不作靜默刪除。
- **媒體總分**：只有累積足夠長期、人工覆核的標註資料後才考慮。
- **重要遺漏自動判定**：只有有可重現的人工作業規則與測試案例後才考慮。
- **單一 EXE**：只有 Release ZIP 對非技術使用者造成可驗證的安裝障礙時才考慮。
- **常駐服務**：只有輪詢延遲被證明不符合實際需求時才考慮。

每一項回加都必須附上失敗案例、量測結果與可回復方案。

## 14. 完成邊界

本規格通過後，下一步只建立實作計畫，不直接開始寫功能。實作仍需分開驗證：

- 本機安裝與卸載。
- 來源輪詢與版本去重。
- provider 錯誤與額度停止。
- 證據可追溯性。
- 可見標註的低誤報邊界。
- 同題分組與使用者介面。

CI 綠燈不代表新聞事實判斷正確；真實 provider、網站可達性、同題分組品質與人工可讀性仍需本機或實際監測證據。
